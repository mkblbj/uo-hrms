# 可直接发给本机 Codex：RLCD 动态二维码＋打卡反馈

用户已批准：ESP32-S3-RLCD-4.2 常驻显示动态打卡二维码，底部显示姓名/成功反馈并播放现有24k语音，让板子替代单独显示 `/qr_display` 的设备。**uo-2f-door 每120秒换码**，员工仍用手机HRMS PWA扫码。请在实际连接板子的本机完成固件，服务器不负责USB烧录或真屏验收。

把本说明与附件 `attendance-sign-qr-display-handoff.zip` 一起转发。包内有本说明、虚构协议样例、二维码绘制参考PNG/模块矩阵和24k签到/签退样音；样例不能用于正式打卡，实际密钥继续沿用本机已有的私有配置，包中不包含密钥。

## 已完成的服务端能力

- HTTPS基础地址：`https://erphr.toiroworld.com`，地点：`uo-2f-door`。
- 新接口：`GET /api/method/hrms.api.attendance_sign.get_qr?location=uo-2f-door`。
- 请求头沿用 `X-Attendance-Sign-Key`，值从本机私有配置读取；User-Agent沿用 `UO-Attendance-Sign/1.0 (ESP32-S3)`。不需要员工登录会话，不把密钥拼到URL。
- 即使网页允许不带展示密钥，新板端接口仍强制校验实际密钥。缺失、错误、跨地点或地点禁用返回403；成功响应不缓存。
- 网页首屏、原 `generate_qr_token` 接口和新板端接口共用相同签名、地点时槽及截止时间。服务器签名密钥留在服务器，板子使用返回的 `token` 直接编码，不自行签名。
- 原 `get_events` / `get_audio` 接口v1、地点密钥、PWA登录及打卡校验不变。二维码取码操作不会创建考勤记录。

## get_qr 响应

Frappe响应仍由 `message` 包装，以下为已过期且签名虚构的样例：

```json
{
  "message": {
    "version": 1,
    "locale": "ja-JP",
    "location": "uo-2f-door",
    "description": "UO 2F 打卡点（示例）",
    "token": "uo-2f-door|14933520|01234567",
    "expires_in": 120,
    "server_time": 1792022410,
    "refresh_at": 1792022520,
    "expires_at": 1792022640
  }
}
```

二维码原始内容就是 `token` 字符串（3段由 `|` 分隔）。不要编码成 `qr_display` 网址，不添加地点密钥、不改变字符或大小写。

- `expires_in` 是本地点的**换码周期**，不是从收到响应起剩余的有效秒数。
- `refresh_at` 是下一次换码的Unix时间；按服务器时间换码，不固定每120秒从设备开机点计时。
- `expires_at` 是这一份token的绝对过期时间。沿用“当前＋上一时槽”规则：120秒一轮，某个码最多从时槽开始有效240秒，并非收到后再延长240秒。
- 例如上面的响应距离换码还有110秒，距离硬过期还有230秒。两个截止时间都需要扣除网络传输耗时，使用单调计时器推进，不能因NTP或系统时钟调整延长有效期。
- `location` 必须和配置一致；无法确认版本、字段或有效期时不要展示新二维码。`description` 为空时可显示地点ID。

## 固件实施顺序

1. **确认目标工程和板子。** 本机仓库有多板、多项目；沿用目标RLCD工程固定的ESP-IDF/LVGL及BSP，不因本次换码功能切换其他项目的框架。若还没有RLCD目标工程，先核对其屏幕、Wi-Fi和音频驱动状态。
2. **先绘制包内虚构样码。** 使用现有LVGL二维码控件或已固定的编码库。300×400竖屏可采用：顶部地点/时间，中央约240～250像素的黑白正方形二维码，底部姓名反馈。绘码按模块整数倍缩放，四边至少4个模块白边，避免抗锯齿、裁切、装饰或文本侵占白边。参考PNG为H纠错等级，仅作像素/白边参考；不要把样例图片当作正式动态二维码。
3. **接入实时取码与计时。** 启动联网后先取码再显示；使用 `server_time`、请求耗时和本地单调计时建立保守截止时间。`refresh_at` 到达后请求新码，完整生成新位图后一次替换二维码区域。一次只保留一个刷新任务，成功取到新码后才更新截止时间；重试不重置旧码有效期。
4. **处理失联和重连。** 刷新失败时，尚未到 `expires_at` 的旧码可暂留并显示连接异常；到期隐藏二维码，显示“离线／二维码暂不可用”。失败按现有网络重试节奏恢复，防止每帧反复请求。重连后取得新码再显示，不长期保留过期码，也不用固定二维码兜底。
5. **保持二维码常驻。** 新增取码任务与现有成功事件轮询、WAV下载/播放分别调度；显示更新由现有UI线程串行处理。扫码成功后只更新底部反馈卡并播报，不全屏遮掉二维码，后面的人继续扫码。姓名文字、语音与事件ID仍配对，沿用当前去重/排队/首连重连基线策略。
6. **保留现有参数。** `get_events` 仍每秒轮询，服务端仍只返回最近30秒的成功记录；这两个值不要改成120。姓名反馈仍按原5秒流程；音频仍为24kHz、PCM16、mono、最长5秒、完整WAV最多262144字节。默认按员工性别或手动声音组选择音色在服务端预生成，板子无需新增性别/TTS逻辑。

## 取码与播报的状态关系

| 情况 | 二维码区域 | 底部与声音 |
| --- | --- | --- |
| 正常待机 | 显示当前有效动态码 | 时间、地点、连接状态 |
| 一人打卡成功 | 继续显示同一有效码，到刷新点正常换码 | 显示姓名/签到或签退/时间，播放24k语音 |
| 多人连续打卡 | 持续可扫，换码不等待语音队列 | 沿用事件队列，不把姓名和语音串人 |
| 取码失败、旧码仍有效 | 暂留旧码，提示连接异常 | 事件和语音按各自网络状态处理 |
| 旧码硬过期 | 隐藏二维码，提示暂不可用 | 不因保留文字而重新展示过期码 |
| 重启/恢复 | 先取有效新码再显示 | 原事件基线不补播历史打卡 |

## 验收与交付

- 使用样包核对二维码解码结果等于 `qr-example.json` 的原始token；这是无效样码，不能代替正式扫码成功测试。
- 正式接口验证HTTPS和密钥，不输出实际密钥；记录周期120、刷新/过期时间和连接状态，避免普通日志持续打印可用token。
- 用常用手机在办公室实际光线、角度和距离下扫码，确认与现有网页相同的PWA流程能打卡成功。不要用脚本向正式站点制造虚构考勤。
- 验证120秒周期中途（尤其经过30/60/90秒）仍能扫码；换码前后、上一轮有效期末和硬过期时行为正确。可在隔离测试里模拟时钟，不修改正式服务器时间。
- 验证连续3人以及上下班高峰：二维码不被姓名卡挡住，音频不阻塞取码，成功事件只回应一次。测试重启、断网跨过过期点、恢复及声音下载失败。
- 先与现有网页显示并行验证，通过后再撤掉原二维码显示设备。交付实际工程/板卡、固件commit、编译烧录结果、真屏扫码及声音结果；未做真板验证须明确标注。

如委派代码审查，按用户要求显式使用 `model="gpt-6-luna"`、`reasoning_effort="medium"`。只实施这一版常驻二维码及原反馈整合，不扩展其他打卡方式。
